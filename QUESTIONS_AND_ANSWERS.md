# Вопросы для проверки проектов по сетевой безопасности

## КОМАНДА 1 — FinGuard Bank (Финансовый сектор)

### Простые вопросы (можно показать на схеме)

#### Вопрос 1.1: Архитектура DMZ
**Вопрос:** Покажите на схеме архитектуру DMZ с двумя уровнями защиты. Объясните, какие компоненты должны быть размещены в каждом уровне и почему именно такая структура обеспечивает безопасность.

**Ожидаемый ответ:**
- **Первый уровень (внешний DMZ):** Reverse Proxy, WAF - первая линия защиты, принимает весь внешний трафик
- **Второй уровень (внутренний DMZ):** Web-портал банка, API сервер, Mail gateway - изолированные сервисы
- Между уровнями должен быть межсетевой экран с правилами фильтрации
- Трафик должен проходить: Internet → FortiGate → WAF → Reverse Proxy → Web/API/Mail
- Внутренняя сеть должна быть полностью изолирована от DMZ, доступ только через строгие ACL

**Что проверить на схеме:**
- Два уровня DMZ четко разделены
- Компоненты правильно размещены по уровням
- Направление трафика показано стрелками
- Firewall правила между уровнями указаны

**Вопрос:** Покажите на схеме распределение VLAN и IP-адресации для минимум 8 сегментов сети. Объясните, почему вы выбрали именно такие подсети и как организована маршрутизация между ними.

**Ожидаемый ответ:**
Пример распределения:
- **VLAN 10 (Admin):** 10.0.10.0/24 - сеть администрирования
- **VLAN 20 (Users):** 10.0.20.0/24 - сеть сотрудников
- **VLAN 30 (ATM):** 10.0.30.0/24 - сеть банкоматов
- **VLAN 40 (Guests):** 10.0.40.0/24 - гостевой Wi-Fi
- **VLAN 50 (Servers):** 10.0.50.0/24 - серверная сеть
- **VLAN 60 (DMZ):** 10.0.60.0/24 - DMZ сегмент
- **VLAN 70 (VoIP):** 10.0.70.0/24 - телефония
- **VLAN 80 (Security):** 10.0.80.0/24 - устройства безопасности (SIEM, RADIUS)

**Что проверить на схеме:**
- Все VLAN указаны с номерами и IP-диапазонами
- Показаны L3 коммутаторы как точки маршрутизации
- ACL между VLAN показаны или описаны
- Логика изоляции сегментов понятна

#### Вопрос 1.3: VPN архитектура для филиалов
**Вопрос:** Покажите на схеме, как организовано VPN-подключение филиалов к центральному офису. Объясните, какой тип VPN вы выбрали (IPSec или WireGuard) и почему, а также как обеспечивается безопасность соединения.

**Ожидаемый ответ:**
- **Тип VPN:** IPSec (Site-to-Site) - более зрелый, лучше поддерживается FortiGate, соответствует требованиям банковского сектора
- **Архитектура:** 
  - Филиал 1 → IPSec туннель → FortiGate ЦО
  - Филиал 2 → IPSec туннель → FortiGate ЦО
- **Безопасность:**
  - Шифрование AES-256
  - Аутентификация по сертификатам или pre-shared key
  - IKEv2 протокол
  - Замена ключей каждые 8 часов
- **Маршрутизация:** Статические маршруты или динамическая через OSPF/BGP

**Что проверить на схеме:**
- Туннели между филиалами и ЦО показаны
- Тип VPN указан
- Параметры безопасности описаны
- Старая L2TP соединение заменено на IPSec

### Сложный вопрос (требует развернутого ответа и схемы)

#### Вопрос 1.4: Zero Trust архитектура и защита от угроз
**Вопрос:** Опишите и покажите на схеме, как реализован принцип Zero Trust в вашей архитектуре банка. Как ваша система защиты противодействует следующим угрозам: MITM-атаки, перехват ATM трафика, DDoS на web-портал, и bruteforce VPN? Покажите на схеме точки контроля и мониторинга.

**Ожидаемый ответ:**

**Zero Trust принципы:**
1. **"Never trust, always verify"** - каждый запрос проверяется независимо от источника
2. **Микросегментация** - строгое разделение сетей с ACL на каждом уровне
3. **Least privilege** - минимальные права доступа
4. **Многофакторная аутентификация** - для VPN и критичных систем
5. **Непрерывный мониторинг** - SIEM анализирует все события

**Защита от угроз:**

**1. MITM (Man-in-the-Middle):**
- TLS/SSL сертификаты на всех соединениях
- Certificate pinning для критичных приложений
- IPSec VPN с проверкой сертификатов
- 802.1X для предотвращения ARP-spoofing
- SIEM мониторит аномальные паттерны трафика

**2. Перехват ATM трафика:**
- Выделенная VLAN для банкоматов (VLAN 30)
- IPSec туннель от каждого банкомата к серверу обработки
- ACL: разрешен только порт 443 к серверу обработки, все остальное deny
- Шифрование трафика end-to-end
- SIEM логирует все соединения банкоматов

**3. DDoS на web-портал:**
- WAF в DMZ фильтрует подозрительные запросы
- Rate limiting на Reverse Proxy
- Geo-blocking на FortiGate для известных источников атак
- CDN (если используется) распределяет нагрузку
- Мониторинг трафика через SIEM с автоматическими алертами
- Резервный канал (провайдер B) для переключения при атаке

**4. Bruteforce VPN:**
- Ограничение попыток входа (3 попытки, затем блокировка на 15 минут)
- MFA обязателен для VPN доступа
- Сильные пароли + сертификаты
- SIEM отслеживает множественные неудачные попытки
- IP whitelist для известных филиалов
- Логирование всех попыток подключения

**Схема должна показать:**
- Точки контроля доступа (FortiGate, WAF, Reverse Proxy)
- SIEM и источники логов (firewall, VPN, AD, IPS, серверы)
- Зоны безопасности с уровнями доверия
- Направления трафика с точками проверки
- Места применения шифрования

**Критерии оценки:**
- Понимание Zero Trust концепции
- Конкретные меры защиты для каждой угрозы
- Интеграция SIEM в архитектуру
- Логичность и реализуемость решений

#### Вопрос 2.1: DMZ для публичных API
**Вопрос:** Покажите на схеме архитектуру DMZ для публичных API. Объясните, как взаимодействуют компоненты: Nginx reverse proxy, API gateway, load balancer. Какой трафик проходит через каждый компонент и почему такая последовательность?

**Ожидаемый ответ:**
**Архитектура:**
- **Внешний трафик** → Palo Alto Firewall → **Load Balancer** → **Nginx Reverse Proxy** → **API Gateway** → **Backend API серверы**

**Роль каждого компонента:**
- **Load Balancer:** Распределение нагрузки между несколькими Nginx инстансами, health checks
- **Nginx Reverse Proxy:** Терминация SSL/TLS, базовая фильтрация, rate limiting, статический контент
- **API Gateway:** Маршрутизация API запросов, аутентификация токенов, версионирование API, метрики

**Последовательность обоснована:**
1. Firewall фильтрует на уровне сети
2. Load Balancer обеспечивает отказоустойчивость
3. Reverse Proxy обрабатывает HTTP/HTTPS
4. API Gateway работает на уровне приложений

**Что проверить на схеме:**
- Правильная последовательность компонентов
- Направление трафика показано
- Показаны backend серверы за API Gateway
- Указаны порты и протоколы (443, 80)

#### Вопрос 2.2: Сегментация сети и VLAN
**Вопрос:** Покажите на схеме разделение сети на VLAN для разных сегментов (Office, Developers, DevOps, Servers, DMZ, Streaming traffic, Guests). Объясните, почему важно разделять трафик разработчиков и DevOps, и как организована изоляция гостевого Wi-Fi.

**Ожидаемый ответ:**
Пример VLAN структуры:
- **VLAN 100 (Office):** 192.168.10.0/24 - обычные сотрудники офиса
- **VLAN 110 (Developers):** 192.168.20.0/24 - разработчики
- **VLAN 120 (DevOps):** 192.168.30.0/24 - DevOps инженеры
- **VLAN 130 (Servers):** 192.168.40.0/24 - серверы в дата-центре
- **VLAN 140 (DMZ):** 192.168.50.0/24 - публичные сервисы
- **VLAN 150 (Streaming):** 192.168.60.0/24 - видеопотоки
- **VLAN 160 (Guests):** 192.168.70.0/24 - гостевой Wi-Fi

**Разделение Developers и DevOps:**
- **Developers:** Доступ к Git, тестовым окружениям, ограниченный доступ к production
- **DevOps:** Полный доступ к Kubernetes, мониторингу, CI/CD, production серверам
- Разделение снижает риск случайного доступа к production из dev-окружения

**Изоляция гостевого Wi-Fi:**
- Отдельный VLAN с полной изоляцией (client-to-client isolation)
- Доступ только в Internet через NAT
- Нет доступа к внутренним сетям
- Captive Portal для аутентификации
- Rate limiting для предотвращения злоупотреблений

**Что проверить на схеме:**
- Все VLAN указаны с IP-диапазонами
- Показана изоляция Guests от остальных сетей
- ACL между VLAN описаны
- Wi-Fi точки подключены к правильным VLAN

#### Вопрос 2.3: Защита трафика между облаком и офисом
**Вопрос:** Покажите на схеме, как организовано защищенное соединение между офисом и Kubernetes кластером в облаке. Какой тип туннеля вы выбрали (IPSec, WireGuard, GRE over IPSec) и почему? Покажите точки входа трафика и маршрутизацию.

**Ожидаемый ответ:**
**Выбор:** IPSec или WireGuard (оба приемлемы)

**Архитектура:**
- **Офис:** VPN-шлюз → IPSec/WireGuard туннель → **Облако:** VPN-шлюз → Kubernetes кластер
- **Маршрутизация:** 
  - Статические маршруты или BGP для динамической маршрутизации
  - Трафик DevOps → Kubernetes API server
  - CI/CD pipeline → Kubernetes для деплоя

**Обоснование выбора:**
- **IPSec:** Стандартный, хорошо поддерживается Palo Alto, совместимость с разными облаками
- **WireGuard:** Современный, быстрый, простая конфигурация, но требует поддержки на обеих сторонах

**Безопасность:**
- Шифрование AES-256
- Аутентификация по сертификатам
- Мониторинг туннеля через SIEM
- Резервный туннель для отказоустойчивости

**Что проверить на схеме:**
- Туннель между офисом и облаком показан
- VPN-шлюзы на обеих сторонах указаны
- Направление трафика к Kubernetes показано
- Резервирование (если есть) отмечено

### Сложный вопрос (требует развернутого ответа и схемы)

#### Вопрос 2.4: Комплексная защита API и противодействие угрозам
**Вопрос:** Опишите и покажите на схеме комплексную систему защиты публичных API от угроз: DDoS-атаки, кража API токенов, SSRF-атаки, и атаки на Kubernetes кластер. Как интегрированы IDS/IPS (Suricata), WAF, rate limiting и ACL? Покажите поток трафика через все уровни защиты и точки мониторинга.

**Ожидаемый ответ:**

**Архитектура защиты API:**

**1. Защита от DDoS:**
- **Palo Alto Firewall:** Базовая фильтрация на уровне сети, Geo-blocking
- **Load Balancer:** Распределение нагрузки, health checks, автоматическое масштабирование
- **Rate Limiting на Nginx:** Ограничение запросов с одного IP (например, 100 req/sec)
- **WAF:** Защита от application-level DDoS (HTTP flood, Slowloris)
- **CDN:** Распределение нагрузки географически, кэширование статики
- **Suricata IDS/IPS:** Обнаружение аномальных паттернов трафика, сигнатуры DDoS

**2. Защита от кражи API токенов:**
- **API Gateway:** Валидация токенов, проверка подписи JWT
- **HTTPS только:** Принудительное шифрование всех соединений (TLS 1.3)
- **Token rotation:** Автоматическая ротация токенов каждые 24 часа
- **Rate limiting per token:** Ограничение использования одного токена
- **Мониторинг:** SIEM отслеживает аномальное использование токенов (множественные IP, необычные паттерны)
- **IP whitelist:** Для критичных API можно ограничить по IP

**3. Защита от SSRF (Server-Side Request Forgery):**
- **WAF правила:** Блокировка внутренних IP в запросах (10.x.x.x, 192.168.x.x, 127.0.0.1)
- **Network segmentation:** API серверы не имеют прямого доступа к внутренним сетям
- **Outbound firewall rules:** Ограничение исходящих соединений с API серверов
- **Suricata:** Обнаружение подозрительных outbound соединений
- **Валидация входных данных:** Проверка URL параметров на сервере

**4. Защита Kubernetes кластера:**
- **Network Policies:** Микросегментация внутри кластера, ограничение pod-to-pod трафика
- **RBAC:** Строгие права доступа к Kubernetes API
- **API Server firewall:** Доступ только через VPN или whitelist IP
- **Pod Security Policies:** Ограничение привилегий контейнеров
- **Мониторинг:** Логирование всех kubectl команд, алерты на подозрительную активность
- **Image scanning:** Проверка образов контейнеров на уязвимости
- **Secrets management:** Использование Kubernetes Secrets или внешнего vault

**Интеграция компонентов защиты:**

**Поток трафика:**
1. **Internet** → 
2. **Palo Alto Firewall** (ACL, Geo-blocking, базовая фильтрация) → 
3. **Suricata IDS/IPS** (mirror port или inline, обнаружение атак) → 
4. **Load Balancer** (распределение нагрузки) → 
5. **Nginx Reverse Proxy** (SSL termination, rate limiting) → 
6. **WAF** (application-level защита, защита от OWASP Top 10) → 
7. **API Gateway** (аутентификация токенов, маршрутизация) → 
8. **Backend API** (обработка запросов) → 
9. **Kubernetes** (если API в кластере)

**ACL между сегментами:**
- **DMZ ↔ DevOps:** Только необходимые порты (например, 443 для API, 22 для SSH с whitelist IP)
- **DevOps ↔ Cloud/Kubernetes:** Только через VPN, порты 6443 (Kubernetes API), 443
- **Office ↔ Servers:** Минимальные права, только для администраторов
- **Guests ↔ Internet ONLY:** Полная изоляция от внутренних сетей

**Мониторинг и логирование:**
- **SIEM собирает логи из:**
  - Palo Alto Firewall (все блокировки, попытки доступа)
  - Suricata (обнаруженные атаки, подозрительный трафик)
  - WAF (блокированные запросы, паттерны атак)
  - API Gateway (использование токенов, ошибки аутентификации)
  - Kubernetes (доступ к API, создание/удаление ресурсов)
  - Nginx (access logs, error logs)

**Схема должна показать:**
- Полный поток трафика через все уровни защиты
- Расположение Suricata (inline или mirror port)
- Интеграцию WAF в поток
- Точки применения rate limiting
- ACL между сегментами
- SIEM и источники логов
- Защиту Kubernetes кластера
- Резервирование компонентов (если есть)

**Критерии оценки:**
- Понимание многоуровневой защиты
- Конкретные меры для каждой угрозы
- Правильная интеграция IDS/IPS
- Логичность архитектуры
- Учет специфики стриминговой компании (высокий трафик, публичные API)
