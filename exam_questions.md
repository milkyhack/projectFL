# Вопросы для защиты проектов по сетевой безопасности

## КОМАНДА 1 — FinGuard Bank (Финансовый сектор)

### Простой вопрос №1
**Вопрос:** Какие VLAN вы создали в своем проекте и для чего используется каждый из них? Покажите на схеме расположение хотя бы трех VLAN.

**Ответ:**
В проекте должны быть созданы минимум 8 VLAN:
- **VLAN 10 - Admin** — для сетевых администраторов и управления оборудованием
- **VLAN 20 - Users** — для обычных сотрудников банка
- **VLAN 30 - ATM** — для банкоматов и терминалов самообслуживания
- **VLAN 40 - Guests** — для гостевого Wi-Fi
- **VLAN 50 - Servers** — для серверной инфраструктуры (AD, RADIUS, SIEM)
- **VLAN 60 - DMZ** — для публично доступных сервисов
- **VLAN 70 - VoIP** — для IP-телефонии
- **VLAN 80 - Security** — для устройств безопасности (IPS, SIEM)

На схеме должны быть показаны коммутаторы с тегированными портами, разделение по этажам и подключение устройств к соответствующим VLAN.

### Простой вопрос №2
**Вопрос:** Что находится в вашей DMZ и почему именно эти сервисы туда помещены? Покажите на схеме.

**Ответ:**
В DMZ должны находиться:
- **Web-портал банка** — публичный сайт для клиентов
- **API сервер** — для мобильных приложений и партнерских интеграций
- **Mail gateway** — для фильтрации входящей/исходящей почты
- **Reverse Proxy** — для защиты внутренних веб-сервисов
- **WAF (Web Application Firewall)** — для защиты от веб-атак

Эти сервисы помещены в DMZ, потому что они должны быть доступны из интернета, но при этом изолированы от внутренней сети. DMZ находится между двумя уровнями защиты: внешним firewall (со стороны интернета) и внутренним firewall (со стороны корпоративной сети).

### Простой вопрос №3
**Вопрос:** Как организована защита сети банкоматов? Какие правила firewall вы применили и почему?

**Ответ:**
Защита сети банкоматов (VLAN 30 - ATM):

**Правила firewall:**
- **РАЗРЕШИТЬ:** ATM → Сервер обработки транзакций (только порт 443/HTTPS)
- **РАЗРЕШИТЬ:** ATM → AD/RADIUS (для аутентификации, только необходимые порты)
- **РАЗРЕШИТЬ:** ATM → NTP сервер (синхронизация времени)
- **ЗАПРЕТИТЬ:** ATM → Internet (прямой доступ запрещен)
- **ЗАПРЕТИТЬ:** ATM → другие VLAN (кроме разрешенных)
- **ЗАПРЕТИТЬ:** Users/Guests → ATM (никто не может подключиться к банкоматам)

**Дополнительные меры:**
- IPS/IDS мониторинг трафика
- Логирование всех подключений в SIEM
- Шифрование трафика (TLS 1.3)
- 802.1X аутентификация на портах коммутатора

Банкоматы — критически важные устройства, поэтому принцип "deny all, permit only necessary" строго соблюдается.

### Сложный вопрос №4
**Вопрос:** Объясните, как реализован принцип Zero Trust в вашем проекте. Приведите конкретные примеры его применения на разных уровнях (сеть, приложения, доступ). Покажите на схеме места применения Zero Trust и объясните, как это защищает от внутренних угроз.

**Ответ:**
Принцип Zero Trust реализован на нескольких уровнях:

**1. Сетевой уровень (Network Segmentation):**
- Микросегментация: каждый VLAN изолирован, трафик между VLAN проходит через firewall
- Даже внутренняя сеть разделена на сегменты (Users, Servers, ATM, Admin)
- Нет "доверенной зоны" — каждое соединение проверяется
- На схеме: все стрелки между VLAN проходят через FortiGate с явными правилами

**2. Аутентификация и авторизация (Identity-based Access):**
- 802.1X с RADIUS для сети сотрудников — устройство должно аутентифицироваться перед получением доступа
- VPN с MFA (многофакторная аутентификация) для удаленных подключений
- Active Directory с ролевым доступом (RBAC)
- Каждый пользователь/устройство имеет минимально необходимые права (Least Privilege)

**3. Уровень приложений:**
- API в DMZ требует токены аутентификации для каждого запроса
- WAF проверяет каждый HTTP-запрос, даже если он идет от "внутреннего" источника
- Reverse Proxy не доверяет запросам по умолчанию

**4. Постоянная верификация (Continuous Verification):**
- SIEM собирает логи со всех источников и анализирует поведение
- IPS/IDS проверяет трафик даже внутри периметра
- Логирование всех действий администраторов

**5. Защита от внутренних угроз:**
- Сотрудник из VLAN Users не может напрямую подключиться к серверам — только через разрешенные сервисы
- Даже администратор должен использовать отдельную Admin-сеть для управления
- При компрометации одного сегмента (например, рабочего места сотрудника), атакующий не получит доступ к другим сегментам
- Банкоматы изолированы даже от сотрудников банка

**Пример сценария:**
Если фишинговая атака скомпрометирует рабочую станцию сотрудника:
1. Атакующий получает доступ только к VLAN Users
2. Firewall блокирует попытки подключения к Servers/ATM/Admin
3. IDS обнаруживает аномальную активность (например, сканирование портов)
4. SIEM коррелирует события и генерирует алерт
5. 802.1X может отключить скомпрометированное устройство от сети

На схеме должны быть показаны: точки проверки на firewall, RADIUS для 802.1X, SIEM для мониторинга, отсутствие прямых связей между сегментами.

## КОМАНДА 2 — BitStream Media (IT/Стриминговая компания)

### Простой вопрос №1
**Вопрос:** Как организована ваша DMZ и какие компоненты в ней размещены? Покажите на схеме и объясните роль каждого компонента.

**Ответ:**
В DMZ размещены следующие компоненты:

- **Nginx Reverse Proxy** — принимает входящие запросы из интернета, скрывает реальную архитектуру, терминирует SSL/TLS
- **API Gateway** — управляет API-запросами, выполняет аутентификацию токенов, rate limiting
- **Load Balancer** — распределяет нагрузку между серверами backend, обеспечивает отказоустойчивость
- **WAF (Web Application Firewall)** — защищает от OWASP Top 10 атак (SQL injection, XSS, и т.д.)

**Схема взаимодействия:**
```
Internet → Palo Alto FW → [DMZ: WAF → Nginx Reverse Proxy → Load Balancer → API Gateway] → Internal FW → Backend Servers
```

DMZ находится между внешним и внутренним firewall. Все публичные сервисы проходят через эту зону, но не имеют прямого доступа к внутренним системам.

### Простой вопрос №3
**Вопрос:** Как вы защитили Wi-Fi сеть? Какие меры безопасности применены и как разделены гостевая и корпоративная сети?

**Ответ:**
Защита Wi-Fi реализована следующим образом:

**Корпоративная Wi-Fi (для сотрудников):**
- **SSID:** BitStream-Corporate
- **Безопасность:** WPA3-Enterprise с 802.1X
- **Аутентификация:** через RADIUS с корпоративными учетными данными
- **VLAN:** зависит от роли (Developers → VLAN 20, Office → VLAN 10)
- **Изоляция:** client-to-client isolation включена
- **Шифрование:** AES-256

**Гостевая Wi-Fi:**
- **SSID:** BitStream-Guest
- **Безопасность:** WPA3-Personal или открытая сеть с Captive Portal
- **VLAN:** VLAN 70 (Guests)
- **Доступ:** только в Internet, запрещен доступ к внутренним ресурсам
- **Изоляция:** полная изоляция между клиентами
- **Ограничения:** bandwidth limiting, короткая аренда DHCP (1 час)

**Firewall правила:**
- Guest VLAN → Internet ONLY (порты 80, 443)
- Guest VLAN → Internal DENY ALL
- Corporate Wi-Fi → Internal (по ролям)

**Физическое разделение:**
На схеме показаны разные SSID на одних точках доступа, но с привязкой к разным VLAN через тегированные порты.

### Сложный вопрос №4
**Вопрос:** Объясните полную цепочку защиты API-запроса от внешнего клиента до backend-сервера в вашей инфраструктуре. Включите все уровни проверки, компоненты безопасности и точки, где может быть заблокирован вредоносный запрос. Покажите на схеме и опишите, как эта архитектура защищает от конкретных угроз (DDoS, injection атаки, кража токенов, SSRF).

**Ответ:**
Полная цепочка защиты API-запроса состоит из нескольких уровней:

**Уровень 1: Внешний периметр (DDoS Protection)**
- **CDN/CloudFlare** (опционально) — фильтрует DDoS атаки, кеширует статику
- **Palo Alto Firewall** — первая линия защиты
  - Rate limiting по IP-адресам
  - Geo-blocking (блокировка стран-источников атак)
  - Проверка на syn-flood, UDP-flood
  - **Защита:** блокирует массовые DDoS атаки на сетевом уровне

**Уровень 2: IDS/IPS (Suricata)**
- Анализ трафика на уровне приложений
- Сигнатуры известных атак (CVE)
- Аномалии в HTTP-заголовках
- **Защита:** детектирует и блокирует эксплойты и сканирование

**Уровень 3: DMZ - WAF (Web Application Firewall)**
- Проверка HTTP-запросов на OWASP Top 10:
  - SQL Injection (блокирует `'; DROP TABLE--`)
  - XSS (блокирует `<script>alert(1)</script>`)
  - Command Injection
  - Path Traversal (`../../../etc/passwd`)
- Валидация Content-Type и размера запроса
- **Защита:** блокирует injection атаки и вредоносный payload

**Уровень 4: Nginx Reverse Proxy**
- Терминирует TLS (только TLS 1.3, сильные cipher suites)
- Проверяет валидность Host заголовков
- Ограничивает методы (только GET, POST, PUT, DELETE)
- Скрывает реальную архитектуру backend
- **Защита:** предотвращает атаки на TLS, скрывает внутренние IP

**Уровень 5: Load Balancer**
- Распределяет нагрузку между backend-серверами
- Health checks — отключает неработающие ноды
- Session persistence (если нужно)
- **Защита:** обеспечивает доступность при атаках

**Уровень 6: API Gateway**
- **Аутентификация:** проверка JWT токенов или API ключей
  - Валидация подписи токена
  - Проверка времени истечения (expiration)
  - Проверка issuer и audience
- **Авторизация:** проверка прав доступа (RBAC/ABAC)
  - Может ли этот пользователь вызвать этот endpoint?
- **Rate Limiting:** по пользователю/токену (например, 100 req/min)
- **Request Validation:** 
  - Проверка схемы JSON (OpenAPI/Swagger)
  - Обязательные поля, типы данных
  - Ограничение размера запроса
- **SSRF Protection:**
  - Валидация URL параметров (запрет internal IP: 127.0.0.1, 10.x.x.x, 192.168.x.x)
  - Whitelist разрешенных доменов для callback URLs
- **Логирование:** все запросы логируются для анализа
- **Защита:** предотвращает несанкционированный доступ, SSRF, abuse API

**Уровень 7: Internal Firewall**
- Разрешает подключения от API Gateway к backend серверам только по нужным портам
- DMZ → Servers VLAN (только порты 5000, 5432 для БД)
- **Защита:** даже при компрометации DMZ атакующий не получит полный доступ к внутренней сети

**Уровень 8: Backend Server**
- Приложение выполняет дополнительную валидацию
- Prepared statements для БД (защита от SQL injection)
- Input sanitization
- Output encoding (защита от XSS)
- **Защита:** defense in depth — последний рубеж

**Уровень 9: Мониторинг (SIEM/Logging)**
- Все уровни отправляют логи в централизованную систему
- Корреляция событий (например, множество неудачных попыток аутентификации)
- Алерты на аномалии
- **Защита:** детектирует атаки в реальном времени, помогает в расследовании

**Защита от конкретных угроз:**

1. **DDoS атака:**
   - Блокируется на уровне CDN/Firewall (rate limiting)
   - Распределяется Load Balancer'ом
   - API Gateway ограничивает запросы по токену

2. **SQL Injection (`' OR '1'='1`):**
   - WAF блокирует вредоносный SQL синтаксис
   - API Gateway валидирует схему данных
   - Backend использует prepared statements

3. **Кража токенов:**
   - TLS шифрование (токен не передается в открытом виде)
   - Короткий срок жизни токенов (15 минут) с refresh tokens
   - Привязка токена к IP/User-Agent (опционально)
   - Логирование использования токенов (детект replay атак)
   - Если токен скомпрометирован — быстрая ротация

4. **SSRF (Server-Side Request Forgery):**
   ```
   Атака: GET /api/image?url=http://169.254.169.254/latest/meta-data/
   ```
   - API Gateway проверяет параметр `url`
   - Блокирует internal IP ranges (10.x.x.x, 192.168.x.x, 169.254.x.x)
   - Whitelist разрешенных доменов
   - Backend делает дополнительную проверку перед HTTP-запросом

5. **Brute-force атака на API:**
   - WAF детектирует множество запросов с одного IP
   - API Gateway rate limiting по токену и IP
   - После N неудачных попыток — блокировка на время
   - CAPTCHA на критичных endpoints

**На схеме должно быть показано:**
```
[Internet] 
   ↓
[Palo Alto FW] ← Rate Limiting, Geo-blocking
   ↓
[IDS/IPS Suricata] ← Signature Detection
   ↓
[DMZ VLAN 50]
   ├─ [WAF] ← OWASP Top 10 Protection
   ├─ [Nginx Reverse Proxy] ← TLS Termination
   ├─ [Load Balancer] ← Distribution
   └─ [API Gateway] ← Auth, Rate Limit, Validation
   ↓
[Internal FW] ← Segmentation
   ↓
[Servers VLAN 40]
   └─ [Backend Servers + DB]
   
[SIEM] ← собирает логи со всех уровней
```

**Дополнительные меры:**
- **Секреты:** API ключи и JWT секреты хранятся в Vault/Secrets Manager
- **Kubernetes:** если backend в K8s, то используются Network Policies для микросегментации
- **VPN для DevOps:** доступ к управлению через VPN с MFA
- **Immutable Infrastructure:** backend servers в контейнерах, легко пересоздать при компрометации

Эта многоуровневая защита реализует принцип Defense in Depth — даже если один уровень обойден, остальные продолжают защищать систему.
